============================================================
1. PROJECT PURPOSE
============================================================

RescueNet AI is a disaster-response AI engine.

It receives disaster reports containing:

- free-text description
- optional image
- latitude
- longitude
- client timestamp
- optional server timestamp
- reporter pseudonym

The engine performs:

1. Incident classification
2. Severity scoring
3. Text + image analysis
4. Multimodal fusion
5. Authenticity verification
6. Duplicate detection
7. Geo/time plausibility
8. Corroboration
9. Human-review flagging
10. Rule-based fallback when AI is unavailable
11. Provenance reporting
12. Structured API responses

The engine is designed to work locally with NO external AI APIs.

12. PHASE 5 — 5 SECOND FALLBACK
============================================================

The project has a rule-based fallback.

Requirement:

AI triage should target p95 <= 5 seconds.

If AI inference becomes unavailable or exceeds the allowed time:

the report must still be processed.

Fallback:

AI unavailable
      ↓
rule-based scoring
      ↓
valid structured result
      ↓
AI_BACKFILL_PENDING

The system must not simply crash.

Possible fallback state:

NORMAL

or:

AI_BACKFILL_PENDING

The fallback is part of the design, not an error in the architecture.

15. PHASE 7 — IMAGE DUPLICATE DETECTION
============================================================

Function:

check_image(image_path, report_id)

Uses:

Pillow
imagehash
perceptual hashing

Algorithm:

image
 ↓
pHash
 ↓
compare against stored hashes

Threshold:

PHASH_DUPLICATE_DISTANCE = 8

Rules:

distance == 0

→ IMAGE_EXACT_DUPLICATE

distance <= 8

→ IMAGE_NEAR_DUPLICATE

otherwise:

→ IMAGE_NOT_DUPLICATE

New valid images are stored in state.json.

Filenames are irrelevant.

The same image with different filenames must still be detected.

Example:

flood.jpg

and:

WhatsApp_Image_2026.jpg

containing identical pixels should be detected as duplicate.

If image processing fails:

IMAGE_CHECK_FAILED

The function must not throw the error to the caller.

If no image is supplied:

return []

No image is NOT suspicious.

17. PHASE 7 — TIMESTAMP PLAUSIBILITY
============================================================

Compare:

client timestamp

against:

server timestamp

If server timestamp is unavailable:

use current UTC time.

Threshold:

10 minutes

If difference > 10 minutes:

TIME_IMPLAUSIBLE

Otherwise:

TIME_PLAUSIBLE

Client time must remain separate from server receipt time.

Client time is important for wait-time/ageing logic later.

============================================================
18. PHASE 7 — IMPOSSIBLE MOVEMENT
============================================================

The system tracks previous reports for the same reporter pseudonym.

Use:

haversine distance

Calculate:

distance / elapsed time

If movement speed > 300 km/h:

IMPOSSIBLE_MOVEMENT

If distance is nonzero and elapsed time is zero:

IMPOSSIBLE_MOVEMENT

Skip this check if:

reporter_pseudonym is missing

or:

no previous report exists.

No external geolocation library is required.

19. PHASE 7 — CORROBORATION
============================================================

Function:

check_corroboration(
    lat,
    lon,
    timestamp,
    incident_type
)

Current thresholds:

MAX_DISTANCE = 500 meters

MAX_TIME_WINDOW = 15 minutes

A nearby report is considered corroborating when:

distance <= 500m

AND:

timestamp difference <= 15 minutes

AND:

incident_type matches

If:

count >= 2

return:

CORROBORATED

and:

NEARBY_REPORTS_<count>

If:

count == 1

return:

WEAK_CORROBORATION

If:

count == 0

return:

[]

Use a simple haversine loop.

DO NOT introduce DBSCAN.

The current implementation is intentionally simple and sufficient for the demo.
